Subject: xeu on E1: receive flow steering, RSS table and interrupt coalescing

Hi <name>,

Thanks again for the call about the receive path. We have acted on
what you told us about reuse: page-pool pages bound to our receive
region are now recycled last in, first out, and your point about
keeping buffers in cache has held up in our measurements.

The next thing limiting us is how flows land on the receive rings, and
we need help from the driver to deal with it.

The setup: an E1 port (xeu 2.0.1, with a few small local patches) on
an arm64 server with 16 KiB pages, 4 RX rings of 256 entries, MTU
9000. A single client writes over NFS on 16 TCP connections
(nconnect=16) at 36 to 38 GB/s.

What we see: which ring a connection lands on is decided by the hash
of its addresses and ports. With 16 flows on 4 rings that spread is
uneven and changes from mount to mount. On one run the rings took 25%,
6%, 31% and 37% of the traffic. Across three runs of the same test,
the run with the worst spread was the slowest: its busiest ring
carried 19.9 GB/s, and the run dropped 440 thousand frames at the ring
tail, where the other two runs dropped about 3 thousand each. That
spread is now the largest source of run-to-run variation we have. With
64 connections the rings come out much more even (28/27/20/25%), as
you said they would, but we would like to control placement rather
than rely on numbers.

What we found in xeu 2.0.1: there is no get_rxfh / set_rxfh, so
`ethtool -x` and `-X` (the RSS indirection table and key) do nothing.
`ethtool -n rx-flow-hash` returns EOPNOTSUPP. ntuple takes exactly one
rule, at location 0, and its target can only be a VF, not an RX ring.
From our reading of the driver source, there are no interrupt
coalescing controls (`ethtool -C`) either. In our profiles,
re-enabling the interrupt at the end of each RX poll accounts for
about 6% of samples.

The SDK built into the module seems to have most of what we need
already. The RM library has:
- xsl_rm_reta_set() and xsl_rm_reta_get(): a redirection table of up
  to 256 ring entries;
- xsl_rm_rss_hash_set() and xsl_rm_rss_hash_get(): a 68-byte seed,
  and which packet types are hashed;
- xsl_rm_rss_hash_type_set(): Spooky, which is the default, Toeplitz
  or symmetric Toeplitz.

xeu does not call any of them. It only calls xsl_rm_rss_configure()
with its list of rings. So exposing the table and the key may be a
small driver change, which we would be glad to write if you can
confirm how these calls behave.

In order of priority, this is what would help us most:

1. RSS indirection table and hash key, through `ethtool -x` / `-X`
   (get_rxfh / set_rxfh), on top of xsl_rm_reta_set/get and
   xsl_rm_rss_hash_set/get. It would let us weight rings and, with
   the key readable and the hash Toeplitz, work out which table entry
   each connection uses and move a busy entry to an idle ring, with
   no remounting.

2. ntuple flow filters that target an RX ring, through `ethtool -N
   flow-type tcp4 ... action <ring>`, and more than one of them, to
   place a single connection on a chosen ring. The table cannot
   separate two busy flows that share one entry; a filter can.

3. Interrupt coalescing / moderation, through `ethtool -C`, ideally
   per ring.

We do not need accelerated RFS. Our server reads its sockets in a way
that does not record a flow's CPU, and any server thread can serve any
connection, so there is no CPU to steer towards.

Our questions:

- How is the redirection table indexed? Is it the low bits of the
  hash, as the RSS group's load-balancing mask suggests, and is its
  size fixed at 256 entries or set by the number of rings?
- Can xsl_rm_reta_set() be called while the port is up and traffic is
  flowing, and do the flows move cleanly?
- With xsl_rm_rss_hash_type_set() set to Toeplitz, is it the standard
  Microsoft Toeplitz over the IPv4/IPv6 TCP 4-tuple, with the seed as
  its key? Which bytes of the 68-byte seed are used for IPv4 TCP?
- Is there a reason the default hash is Spooky (PP_RSS_DEFAULT_HASH)
  and xeu does not expose these calls: a firmware limitation, or a
  known problem?
- Can the ntuple rule target an RX ring instead of a VF, and can there
  be more than one rule? If not in xeu, can the flow table (the "FT"
  RSS groups, xsl_rm_ft_rss_group_set()) steer a single TCP flow to a
  ring?
- Can interrupt moderation be set, and per ring?

Any hardware documentation on the RSS block, the flow filters and
interrupt moderation would also help us.
