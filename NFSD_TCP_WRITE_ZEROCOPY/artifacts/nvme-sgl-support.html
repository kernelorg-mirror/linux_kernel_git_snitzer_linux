The kernel isn't the cause. Every 7.1 kernel carries bc840b21a25a, and nvme_pci_get_virt_boundary() returns 0 exactly when the controller advertises SGLs. sgl_threshold doesn't affect it. So 4095 means these controllers don't support SGLs; nvme id-ctrl /dev/nvmeX | grep -w sgls should read 0.

On tardis1 as equipped, neither phase makes loaned WRITEs direct.

  • Phase 1 behaves correctly. These exports report dio_seg_boundary=4096, so the gate keeps the joint rule and WRITEs with mid-page joints go buffered, as before phase 1.
  • Phase 2 can't help here. rx_ip_align=2 fixes the 4-byte offsets, but every frame boundary is still a mid-page joint, which a 4096 boundary refuses. A tardis1 run would show the aligned offsets in loan-geometry.bt, not a change in dispositions.
  • What a PRP-only device needs is page-tiled payload, with every joint on 4096. On E1 that means header-data split with payload coalescing, the firmware ask in the NFSD Page Loan document, or SGL-capable NVMe in tardis1.

The problem

Loaned payload has mid-page joints that PRP-style devices refuse

A loaned WRITE hands the file system the NIC's own receive pages. That is one fragment per TCP segment, about 1448 bytes each at MTU 1500, and every joint between fragments falls in the middle of a page. Before phase 1, nfsd's direct I/O gate assumed every device had a 4 KiB virtual boundary. It demoted any WRITE with a mid-page joint to buffered, because a bio carrying one would be split off a logical block and fail with -EINVAL.

That assumption is wrong for a large class of devices. Two block-layer rules decide what a device takes:

virt_boundary_mask — every interior joint must fall on this boundary. Gaps elsewhere force a split, and a split off a logical block is -EINVAL.
per device
dma_alignment — each bvec's offset and length must be multiples of this. NVMe uses 3, meaning 4 bytes.

Are the loaned pages still needed if the device does SGL? Yes. SGL removes the page-tiling requirement, not the copy. Without the loan, SUNRPC still copies the payload into rq_pages, which are already page-tiled, so SGL alone saves nothing. The two together are what let the NIC's own pages reach NVMe without a copy.

Does NVMe actually pick SGLs?

A loaned WRITE is gapped, so an SGL-capable controller always uses SGLs for it, whatever sgl_threshold says.

nvme_pci_use_sgls() returns SGL_FORCED when the request's physical gap mask crosses the controller page (gaps are tracked per bio since 2f6b2565d43c). The 32 KiB average-segment heuristic applies only to gap-free requests. A PRP-only controller keeps boundary 4095, so nfsd demotes those WRITEs instead of risking -EINVAL.

This rig has no SGL-capable PCIe NVMe, so this was confirmed from the source only. The NVMe/TCP rows stand in for it.

Phase 2 · xeu receive placement

Two more bytes of headroom align every E1 payload

Phase 1 lets an SGL device take mid-page joints, but each fragment must still start and end on 4 bytes. The xeu driver posts every RX buffer at dst_addr = dma_addr + XEU_RX_PAGE_HEADROOM, with headroom NET_SKB_PAD + NET_IP_ALIGN. On arm64 those are 64 and 0 (measured with a probe module).

frame start 64 0 mod 4 IP header (after 14-byte Ethernet) 78 2 mod 4 TCP payload, no options 118 2 mod 4 TCP payload, timestamps 130 2 mod 4 with rx_ip_align=2, payload 132 0 mod 4

IPv4, IPv6 and TCP headers, options included, are always multiples of 4 bytes, and a VLAN tag adds 4. So every plain Ethernet TCP payload is 2 mod 4, and two more bytes of headroom make all of them 0 mod 4. This is the classic NET_IP_ALIGN = 2 placement. Fragment lengths are TCP payload sizes: MSS 1448 and 8948 are both multiples of 4.

Δ

A load-time parameter, default offnew

rx_ip_align=0 posts exactly what the driver always posted, 2 adds the headroom, and other values are ignored with a warning. Every use of the headroom and buffer data size goes through two helpers: refill posting, skb_reserve(), the linear and fragment lengths, skb_add_rx_frag() and max_rx_buf_per_pkt. The parameter is read-only (0444): a buffer must be parsed with the headroom it was posted with.

✓

The headroom applies to every RX buffer the driver posts, not only a frame's first. One buffer holds PAGE_SIZE - 66 - 320 bytes of frame (headroom, then skb_shared_info): 3710 bytes on 4 KiB pages, 65150 on 64 KiB pages.

The 64 KiB kernel is the only configuration where jumbo frames, the MTU a storage network runs, land entirely aligned. The driver warns when the MTU makes a frame span several buffers. Fixing 4 KiB jumbo would need the E1 to pad only a frame's first buffer (Xsight question 2).

Checking an export NVMe

Find the namespace under the export first. If the source is a partition, use its parent namespace, for example nvme0n1. Then read its queue limits from sysfs:

findmnt -no SOURCE /path/to/export

d=/sys/block/nvme0n1/queue
cat $d/virt_boundary_mask $d/dma_alignment $d/logical_block_size
virt_boundary_mask is 0: no boundary, so mid-page joints are accepted
placement helps
virt_boundary_mask is 4095: PRPs only, and loaned WRITEs fall back to buffered whatever the NIC does
stop
dma_alignment is 3: payload must be 4-byte aligned, which rx_ip_align=2 gives
expected

sysfs doesn't show whether the controller supports SGLs, so ask nvme-cli. The low 2 bits must be non-zero: 1 means SGLs are supported, and 2 means they are supported with 4-byte alignment. Either works here. 0 means no SGLs, and then the mask will be 4095. Also leave the SGL threshold at its default of 32768. It only affects requests without gaps, so loaned WRITEs get SGLs regardless, but 0 turns SGLs off.

nvme id-ctrl /dev/nvme0 | grep -w sgls
cat /sys/module/nvme/parameters/sgl_threshold      # default 32768; 0 disables SGLs

# every namespace at once
for d in /sys/block/nvme*n*; do
  echo "${d##*/} vbm=$(cat $d/queue/virt_boundary_mask) dma=$(cat $d/queue/dma_alignment)"
done

If the export sits on dm or md rather than directly on the namespace, check the top device's queue/ too: it takes the strictest limit of the devices beneath it. Once tardis1 runs the phase 1 kernel, statx-dio on a file in the export gives the same answer end to end: dio_seg_boundary=0.

For comparison, the qualification box's own nvme0n1 is PRP-only, which is why phase 1 was qualified over NVMe/TCP instead:

nvme0n1 vbm=4095 dma=3
sgls      : 0

Making rx_ip_align permanent

There are two ways to set the parameter. Put options lines in /etc/modprobe.d/; /etc/modules-load.d/ only lists modules to load and doesn't take parameters.

1

modprobe.d

This applies every time xeu loads, by udev at boot or by a manual modprobe. If xeu is in the initramfs, rebuild it so the copy there sees the option.

echo 'options xeu rx_ip_align=2' > /etc/modprobe.d/xeu.conf
dracut -f --kver <release>                       # only if xeu is in the initramfs
lsinitrd /boot/initramfs-<release>.img | grep -E 'xeu|modprobe.d'
2

Kernel command line

modprobe reads /proc/cmdline and applies module.param=value entries to modules it loads, so this works for a loadable xeu too. It takes effect from the next boot, and only for the kernels you updated.

grubby --update-kernel=/boot/vmlinuz-<release> --args="xeu.rx_ip_align=2"
grubby --update-kernel=/boot/vmlinuz-<release> --remove-args="xeu.rx_ip_align"   # undo

For the tardis1 A/B, use the command line on one grub entry.

Leave the known-good entry without the parameter, so going back is just choosing the other entry at boot. A modprobe.d file affects every kernel and needs editing to undo.

Check the value after load, either way. The parameter is read-only after load, so a new setting takes effect only when xeu loads again, either with modprobe -r xeu && modprobe xeu or by rebooting. Reloading takes the link down, so follow the deadman-switch procedure in section 0 of TESTING.md.

cat /sys/module/xeu/parameters/rx_ip_align   # expect 2
dmesg | grep rx_ip_align                     # no "spans N RX buffers" warning

Tracing the two passes

trace-loans.sh, next to loan-geometry.bt in xeu-SGL-compat-receive-placement/, runs the geometry probe and counts nfsd WRITE dispositions over one interval. It saves both, with the run's settings, under out-LABEL-<timestamp>/. Start the client WRITE load first, with loans on:

./trace-loans.sh passA-rx0 60      # stock module, or rx_ip_align=0
./trace-loans.sh passB-rx2 60      # after reloading xeu with rx_ip_align=2

On hs.441 the probe is sound: svc_tcp_rx_append is a real function in the 64K sunrpc.ko, and both the borrowed and copied paths call it. On tardis1, judge the run by @offset_mod4 for the NIC-loan fragments (@page_pool[1]), which should move from 2 to 0 mod 4. The E1 accepts a receive address that is 2 mod 4, and every loaned fragment lands 4-byte aligned. The ~6% fewer bytes in pass B comes from one run each, back to back, so it doesn't yet show a rate penalty.

On 64 KiB pages a WRITE never completes as a loan: the table holds 20 fragments.

The per-record loan table is sized in pages, DIV_ROUND_UP(sv_max_mesg, PAGE_SIZE) + 3: 260 entries on 4 KiB, 20 on 64 KiB. Every loaned fragment takes an entry, however short it is. A WRITE therefore loans about 20 segments, then hits the capacity fallback, and svc_tcp_rx_materialize() copies the whole record into the page-tiled arena, which goes direct on PRP NVMe.

borrowed bytes per WRITE 346,882 ≈ 20 fragments × ~17 KB WRITE disposition: direct 99.3% copied arena, not the loan svc_tcp_rx_materialize / WRITE 478,415 / 465,720 ≈ 1.03

So rx_ip_align could not move the dispositions, and neither could SGL NVMe. The fix belongs to the parent series: size the table for fragments, not pages. It hasn't been made.

Also seen: every WRITE on the wire was exactly 1,000,000 bytes, although fio issues 1 MiB. Only 1 in 64 is 4 KiB-aligned, so each WRITE gets a buffered head and tail around its direct middle. Where that chunking happens, in the client or the metadata-server path, is still open.

Open items

What stands between here and tardis1

For phase 2 to pay off on E1

  • An SGL-capable export NVMe — tardis1 has none. All nine namespaces are PRP-only (table above). Phase 2 needs an E1 host with SGL-capable NVMe; otherwise the E1 needs header-data split with payload coalescing.
  • An HS kernel, now building. kernel-7.1/hs-7.1.13-14.NFSD_TCP_WRITE_ZEROCOPY carries the series, the merge top-up fix and SGL phase 1 under the Hammerspace DP commits. tardis1 needs its 64 KiB page build.
  • kmod-xsight with the patch, built through kernel-rpmtree against the new kernel-devel (RHEL configs), 4 KiB and 64 KiB flavors; modinfo -p must show rx_ip_align in both.

Questions for Xsight

  • Does the E1 RX DMA engine accept a dst_addr that is 2 mod 4 at full rate, with no alignment requirement or penalty?
  • Can the RX path pad only a frame's first buffer? That would align continuation buffers too, and so jumbo frames on 4 KiB pages.
  • Encapsulated traffic (VXLAN or Geneve inner Ethernet) shifts the payload by 14 bytes and breaks the rule. Is it in scope for NFS storage traffic on E1?

Decisions for Mike

  • The loop commit b2dc54218a0b: keep it in the series or send it on its own.
  • A runtime-changeable rx_ip_align: read it per device at xeu_open() so a link down/up applies a new value without reloading the module.

Remaining coverage

  • KUnit on a 64 KiB page kernel: the walk built both page sizes, but only the 4 KiB kernel ran the tests.
  • SGL selection observed on real SGL-capable PCIe NVMe, which this rig doesn't have.
