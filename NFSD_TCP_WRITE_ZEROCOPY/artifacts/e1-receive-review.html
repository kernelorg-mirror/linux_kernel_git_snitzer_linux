E1 receive path · NFS writes on an arm64 server · 21 October 2026

The card carries line rate on both ports.What holds NFS back is the server's copy, and the loan removes it.

An NFS server on the E1 takes 60.4 GB/s of durable WRITEs from one client over both ports of the card, and 47.8 GB/s over one: sixteen connections a port, copied once on arrival and written direct to eight NVMe drives, each with its own file system. One port is at 96% of what the wire carries to a receiver that stores nothing (49.8 GB/s), and six days earlier the same copy carried 25.4. Two ports are at about what this machine can copy from memory to memory by any method. The receive memory in use stays inside the CPU's 32 MiB cache. Three settings do it together: the card's receive buffers cut to 8192 bytes with the MTU lowered so that each frame fills one, each connection's receive buffer held at 1 MiB, and every connection placed on a receive ring so that each ring carries a quarter. Both are the best run of their setting: one port gave 46.0 to 47.8 in six runs on Linux 7.3 (46.5 to 47.4 in four on 7.1), and two ports 60.0 to 60.4 in seven on 7.1.

This page sets out what we measured since your two replies, what we would like from you, and what we can give back.

Denser buffers keep more data in the cache. The same rings and the same held buffer hold more payload in less memory, so the copy finds its data in cache more often: its share of the server's cycles is 25% at 8192 bytes against 29% at 5440. It is the one change that raised the rate and lowered the memory together. A fifth more frames arrive for the same data, and the rings took them with 9 and 7 dropped.

One buffer to a frame also matters for what comes next. With two buffers to a frame the second is not placed on a 4-byte boundary, which a direct write of loaned pages needs. With one, every piece is placed. Only the server's MTU is lowered; the client's stays at 9000.

Around the buffers, three settings. A 1 MiB held receive buffer is worth about 1.7 GB/s over 685 KiB: more of a WRITE has arrived when a thread reads it. Rings of 256 frames drop next to nothing where rings of 128 dropped a hundred thousand to nine hundred thousand frames a run. And placing every connection on a ring made runs repeat: two runs of a setting are within about 1 GB/s, where the same setting had given 41.0 and 36.6.

What the peak depends on

Four things have to hold at once. Take any one away and the rate falls or stops repeating.

1

One copy, written direct

nfsd copies a WRITE out of the receive pages once and the file system sends that buffer to the drives as it is. A second copy through the page cache held the same load to 25 GB/s.

2

A connection that never waits for data

A receive buffer deep enough to hold a whole WRITE, and one thread that stays with the WRITE until it is all in. With a shallow buffer each connection sat idle for more than half the time.

3

Receive memory that stays inside the L3 cache

Receive buffers a frame fills (8192 bytes at an MTU of 7792), rings sized in frames, and pages reused last in, first out. Copying a WRITE takes 60% longer when the memory in use grows from 24 MiB to 48 MiB; the best setting uses 24 to 26.

4

Every flow placed, so each ring carries a quarter

Each ring is served by one CPU, so the busiest ring is the first thing to run out. Left to the card's hash, sixteen connections have put 36% to 42% of the traffic on one ring and as little as 6% on another, differently at every mount. In an earlier set of three like runs the slowest was the one with a ring at twice its share. The harness now reads each connection's hash and sets the card's RSS table so that four connections land on each ring. Under NFS the rings went from 23, 21, 36 and 20% to 25.0, 25.0, 25.4 and 24.6% (below), and two runs of one setting now come within about 1 GB/s of each other where they differed by more than 4.

What we brought to it. By 9 October there had been a week of runs on the card, and so the call could be about how a buffer lives and not about which features the card lacks. The measurements already said that the wire carries line rate when nothing has to be stored, that the copy stopped near 25 to 28 GB/s, that the client spent its time waiting on the server, that the receive memory was being held inside the 32 MiB cache with back pressure to the sender, and that the page pool's locking was one of the costs. Earlier requests to Xsight had been for features other cards have, such as header-data split and coalescing of received frames. With those figures in hand the question put to them was a better one: how does a buffer have to move for this hardware to perform?

What Xsight said. A buffer has to be used again while it is still in the cache, so its whole life, from the ring to the copy and back to the pool, must fit in the cache's footprint. The buffer freed last should be the one allocated next, as DPDK does. One burst of delay can push the buffers out of cache into a slower state that does not recover, so try a load paced at the source and raised in steps. Flows reach the rings by the hash of their addresses and ports, so an even spread needs many more flows than rings, and is read from the per-ring counters as differences. More rings, or deeper ones, is more memory posted.

One port of the card, a separate client machine, Linux 7.1 and xeu 2.0.1 with the patches below.

Only the server's MTU is lowered. The client keeps 9000, and nothing on the client changes.

Why that works. When a TCP connection opens, each end tells the other the largest segment it will accept, worked out from its own MTU. The server now says 7752 bytes. A sender never exceeds what the receiver asked for, so the client cuts its data into segments the server's buffers hold, whatever its own MTU is. Measured on the client during a run: its connections to the server use a segment size of 7740 bytes (7752 less the 12 bytes of TCP timestamps) while its own port still reports an MTU of 9000.

Why it is safe. The limit is agreed for each connection, by the two ends, before any data moves, so there is nothing to fragment and nothing to discover along the path. In the other direction the server sends frames of at most 7792 bytes, which a 9000-byte port accepts. Nothing between the two hosts needs changing, and the client's other traffic, to other servers, still uses 9000.

The one limit. This protects TCP only. A single packet larger than 7792 bytes that is not TCP, such as a large ping or a large UDP datagram, has no such agreement and does not get through: an 8500-byte ping from the client to the server goes unanswered, where a 7792-byte one is answered. NFS here runs over TCP, including the mount, so it is not affected.

A WRITE that one thread began receiving and another finished had its pages freed and allocated again at each handover. They are now swapped. The page allocator left the profile.

A 1 MiB WRITE arrives as about 118 jumbo frames, which the network stack hands up a burst at a time. nfsd read whatever had arrived and, if the WRITE was not complete, parked it on the connection and went on to other work; the next burst woke some thread to read the next piece.

What the pieces cost. Every extra read is a thread woken and a WRITE handed over. In between, the rest of the WRITE sits unread in the connection's receive queue, in pages that came off the rings, and those pages cannot go back to the pool until some thread gets to them. So the receive memory in use is larger, the rings are refilled with pages that have been idle longer, and the connection's window stays shut to the client. With the 256 KiB buffer a connection was being read for only 44% of the time: for 38% it was waiting for data and for 18% for a thread. A piece is about 13 µs in coming, so a wait far shorter than a wake-up keeps one thread on the WRITE until it is whole.

With the wait and the other changes loaded together, frames dropped at the rings fell from 251 thousand to about 3 thousand in the same run on rings of 4 x 256; how much of that is the wait alone has not been measured. It is a busy wait and costs about a fifth more server CPU per GB (0.52 against 0.43 CPU-seconds), and how short it can be is not settled.

4

Several nfsd thread pools on one NUMA nodesunrpcdropped since

All 512 threads took ready connections from one queue. Four pools give four queues. Its own worth has not been measured: the load that showed the contention had 64 connections.

5

The page pool reuses a region's pages last in, first outpage_pool

A pool bound to the region recycled through a first-in, first-out ring, so the page handed to the card next was the one idle longest and least likely to be in cache. It is now a stack. The count of pages turned away from a full ring went to 0 with the smaller buffers.

The loan, for NVMe drives with SGLs · 16 KiB
10 October

Ready for SGL drives: every loaned WRITE is written direct, at less than half the CPU of a copy

Everything above is copy mode, which is the right answer for drives that need whole pages. NVMe drives that support SGLs, and those can take a WRITE's network pages as they arrived, with no copy at all. NVMe over TCP was their stand-in on 10 October, so that the whole path was in place before such drives were on hand; the alignment result near the top of this page is on real SGL drives.

On 8192-byte buffers with the MTU at 7792, all 2.5 million loaned WRITEs of a run were written direct. None fell back to the page cache.

What a direct write of loaned pages needs. Each piece of a WRITE handed to the storage must start on a 4-byte boundary. nfsd checks every piece, and one that fails sends the whole WRITE through the page cache: the copy comes back, later. The card places a frame's data on a boundary in the first buffer it uses and not in a second. So the setting that carries the most in copy mode is also the one a loan needs: one buffer to a frame.

Read the CPU, not the rate. NVMe/TCP on the same host copies the data once more on its way to the file and uses the same CPUs to do it, so neither rate is what a real SGL drive will give. The loan's rate did not move when its budget was changed, which says the stand-in's storage is its limit. The price is the one a loan always pays: it holds receive memory until the storage has finished the write, 45 to 50 MiB here, past the 32 MiB cache.

The charge for a loan: the kernel now learns it

A budget limits how much receive memory loans may hold. Each WRITE is charged, when it starts, for the pages it is expected to hold, and that estimate was a setting someone had to get right: svc_tcp_rx_credit_factor. The right value depends on how the card cuts its pages into buffers and on how the frames of different connections fall into them. With two buffers to a page, a 1 MiB WRITE holds 68 pages if its frames pair up and up to 136 if each shares its page with another connection's.

Too high wastes the budget; too low stalls WRITEs half received. The figure for a whole page to a frame was stale once the buffers changed and admitted about nine WRITEs where sixteen were meant. The neat figure was too low, because frames do share pages. A new kernel change removes the guess: each budget watches what its own WRITEs actually held and charges the next ones by the most any of the last one to two thousand did. The setting is removed: the receive window is measured too

The same setting did a second job, and that one reached copy mode. It told the kernel how much memory a connection's packets take up for each byte of data, which decides how much receive window a held buffer can offer. It had been set to 190 by hand, right for a whole page to a frame; on 8192-byte buffers the true figure is 107. The kernel now measures it on each connection, from the packets it reads, and svc_tcp_rx_credit_factor no longer exists.

Our server copies each write out of the receive buffers once. Each copied byte costs about 2.2 bytes of traffic to the server's DRAM, so 60 GB/s of NFS is about 131 GB/s of memory traffic. That is close to what a bare memory-to-memory copy reaches on this server (62 to 68 GB/s). This is the server's DRAM, not the E1's; there is nothing to look for on the card here.

The way past it is not to copy. That is the receive-page loan: the server hands the received pages themselves to the storage.

Copy

  1. The card writes frames into receive pages.
  2. The server copies the write's data out.
  3. The receive pages go back to the card.
  4. The copy is written to the drives.
about 2.2 bytes of DRAM traffic for each byte

Loan

  1. The card writes frames into receive pages.
  2. The server hands those pages to the drives.
  3. The drives write them as they arrived.
  4. Only then do the pages go back to the card.
no copy; about 0.1 bytes for each byte still in cache

A loaned page can go to an NVMe drive directly only if each piece of it meets the drive's DMA alignment, 4 bytes. Where the payload lands in the receive buffer decides that, which is the first item below.

The strongest result

Payload alignment decides whether a loaned write goes to the drive

xeu posts each receive buffer at NET_SKB_PAD (64 bytes) and a frame's headers take 54, so every TCP payload starts at 2 mod 4. NET_IP_ALIGN is 0 on arm64 for good reason, the CPU's unaligned loads of the IP header are cheap, and our patch is not about that. It is about the payload, for the storage DMA. Our patch's subject led with the IP header, which invited the misreading.

Measured on a server whose drives take scatter-gather lists with dword alignment and no other boundary, so the payload's alignment is the only thing that decides. NFS writes onto two of those drives, each write's received pages handed to the drive without a copy, two runs at each setting:

6. Keep an interrupt placement across a close and open

patch offered

We agree that spreading across ports is for the host. What the host cannot do is keep a placement: xeu_close() frees the interrupts and disables MSI-X, which resets their affinity, so every open puts them back on CPUs 0 to 7. That includes the async ring, which has no hint, so changing only the hint call would not be enough. Our patch records each interrupt's affinity at close, restores it at open, and sets xeu's spread only as the hint (irq_update_affinity_hint(), as mlx5, bnxt and i40e do).
