The card carries line rate on both ports.What holds NFS back is the server's copy, and the loan removes it.

An NFS server on an E1 takes 47.8 GB/s of durable writes from one client on one port and 60.4 GB/s on two, copying each write once on arrival. The card itself carries both ports at line rate when nothing is copied. This page sets out what we measured since your two replies, what we would like from you, and what we can give back.

Our server copies each write out of the receive buffers once. Each copied byte costs about 2.2 bytes of traffic to the server's DRAM, so 60 GB/s of NFS is about 131 GB/s of memory traffic. That is close to what a bare memory-to-memory copy reaches on this server (62 to 68 GB/s). This is the server's DRAM, not the E1's; there is nothing to look for on the card here.

The way past it is not to copy. That is the receive-page loan: the server hands the received pages themselves to the storage.

Copy

  1. The card writes frames into receive pages.
  2. The server copies the write's data out.
  3. The receive pages go back to the card.
  4. The copy is written to the drives.
about 2.2 bytes of DRAM traffic for each byte

Loan

  1. The card writes frames into receive pages.
  2. The server hands those pages to the drives.
  3. The drives write them as they arrived.
  4. Only then do the pages go back to the card.
no copy; about 0.1 bytes for each byte still in cache

A loaned page can go to an NVMe drive directly only if each piece of it meets the drive's DMA alignment, 4 bytes. Where the payload lands in the receive buffer decides that, which is the first item below.

The strongest result

Payload alignment decides whether a loaned write goes to the drive

xeu posts each receive buffer at NET_SKB_PAD (64 bytes) and a frame's headers take 54, so every TCP payload starts at 2 mod 4. NET_IP_ALIGN is 0 on arm64 for good reason, the CPU's unaligned loads of the IP header are cheap, and our patch is not about that. It is about the payload, for the storage DMA. Our patch's subject led with the IP header, which invited the misreading.

Measured on a server whose drives take scatter-gather lists with dword alignment and no other boundary, so the payload's alignment is the only thing that decides. NFS writes onto two of those drives, each write's received pages handed to the drive without a copy, two runs at each setting:

What we would like from you

Seven points, each with what it rests on

1. Align the payload, and continuation buffers too

ask

The table above is the case for reconsidering rx_ip_align. A driver can shift the first buffer of a frame, but with receive buffers smaller than a frame the payload in each continuation buffer is misaligned by the same 2 bytes, and only the card can fix that.

QuestionCan the E1 shift only a frame's first buffer, with a receive pad or by splitting headers from data, so that every buffer of a frame is aligned?

QuestionsHow long can the XDMA engines wait on memory before the 2 MiB FIFO (about 40 µs at this rate) overflows? Is there a setting that gives the port's DMA priority, or more FIFO, on a host whose memory is busy?

3. Pause frames never reach the wire

ask

With the client set to obey pause and memory loaded so that the FIFO overflows: with ethtool -A tx on the FIFO passes xoff (15,638 lines against 12,288) and drops 419,218 frames, and the client receives no pause frame. With rx on tx on the rings drop nothing, the FIFO holds at 12,113 lines, just under xoff, and drops 1,458,125 frames; still no pause on the wire. The port appears to act on xoff by dropping.

QuestionIs there a setting for the MAC to send pause?

4. Interrupt deferral stops the port

ask

Under load the port takes 6.3 million frames and about 250,000 Rx interrupts a second. With napi_defer_hard_irqs=2 and gro_flush_timeout=50000 written to the port, Rx interrupts fall to 0 in the first second and stay there. Frames keep arriving for about 5 s without an interrupt (4.3, then 2.2 million a second), then stop. Writing both back to 0 does not recover the port; only a down and up does. Nothing is logged. Reproduced on two kernels.

LeadThe interrupts stop at once while NAPI still runs for a few seconds. A script reproduces it with plain TCP, no NFS.

5. The RSS hash

ask

Thank you for the input fields. We tried them on ten TCP flows into one port with Toeplitz selected, each from a known client port, hashes read from received packets; the key is the standard 40-byte one followed by 28 zero bytes. Neither the 13-byte input (source address, destination address, source port, destination port, protocol) nor the standard 12-byte one reproduces all ten hashes, at any of the key's 68 starting bytes, with either byte order for the fields or the result.

Confirmed: bits 13 to 19 of the hash pick the entry of a 128-entry redirection table, for every flow. Also: selecting Toeplitz with the ethtool command fails because the default function has no ethtool name; setting it over netlink works.

QuestionThe exact computation: which bytes of the key, in what order, and anything applied to the result.

6. Keep an interrupt placement across a close and open

patch offered

We agree that spreading across ports is for the host. What the host cannot do is keep a placement: xeu_close() frees the interrupts and disables MSI-X, which resets their affinity, so every open puts them back on CPUs 0 to 7. That includes the async ring, which has no hint, so changing only the hint call would not be enough. Our patch records each interrupt's affinity at close, restores it at open, and sets xeu's spread only as the hint (irq_update_affinity_hint(), as mlx5, bnxt and i40e do).

7. rx_refill_thresh: derive it from the ring size

our answer to your question

You asked whether the threshold should vary with the use case. It should vary with the ring size, and the driver can work that out itself. NFS writes in copy mode, 32 against 8 by turns, three runs each, over 10 s:

Threshold 32Threshold 8
Two ports, rings of 128: ring drops a port2,845–5,3171–15
Two ports, rings of 128: client retransmits8,304–11,29934–224
One port, rings of 256: ring drops7–220
One port, rings of 256: rate45.4–46.4 GB/s45.8–46.6 GB/s

On rings of 128, 32 leaves a quarter of the ring empty before a refill and the rings drop; on rings of 256 it is an eighth and makes no difference. Something like min(32, ring size / 8) keeps your default where it works, needs no parameter, and we would drop our patch.
