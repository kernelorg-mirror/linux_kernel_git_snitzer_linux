One CPU copy, landing kept on-die.
First, prove the NIC writes stay in cache.

David Flynn's idea for PRP-only NVMe: accept one CPU copy of each WRITE payload, but take it promptly from a small receive area that stays in on-die cache, so only the back-end copy goes to DRAM. Today's copy path already has this shape. What it lacks is a prompt copy and a small landing set, and nobody knows yet whether E1's receive writes land in cache at all.

The idea

Make the one DRAM round trip the back-end one

On tardis1 every NVMe namespace is PRP-only, so loaned NIC pages can't go O_DIRECT: each TCP segment is a fragment ending mid-page, and the admission gate demotes the WRITE to a page-cache copy. David's answer is to stop fighting the copy and control where it happens:

1

Accept one CPU copy

Two data movements per written byte are fine, as long as only one of them goes out to DRAM and back.

2

Copy promptly from a small landing area

Copy within about 10 µs of landing, from receive buffers confined to a few MB, so the NIC write and the copy read both stay in on-die cache. A core or two could be dedicated to it.

3

Release the landing buffer before storage completes

The copy destination absorbs NVMe latency, including its multi-millisecond tails; the landing area only has to cover the copy.

The 10 µs and few-MB figures are David's starting guesses. The spec replaces them with a residency model that needs the system cache size, which nobody has yet.

The 2-touch case also needs the next NIC write to overwrite the dirty landing line in cache, with no write-back to DRAM. If the copy's stores read the destination line first (RFO), add one DRAM read to every copy row.

What the tree already does

Today's copy path is David's data path, minus the physics

With loans off, or for any record that isn't loan-eligible, SUNRPC's read_sock actor copies the payload into the nfsd thread's own rq_pages (svc_tcp_rx_copy_skb(), svcsock.c:1698). The skb is unlinked in the same pass, before decode, storage or reply. The destination is page-tiled, so nfsd's split sends its middle segment O_DIRECT even on a 4095 boundary.

Why the copy isn't prompt

  • The copy waits for an idle nfsd thread, and the thread that copies a record then runs it: a synchronous O_DIRECT write through NVMe completion, plus fsync for stable writes. tardis1's workers were 86% busy.
  • nfsd threads are dynamic. A wake with no idle thread spawns nothing; a new thread appears only after a running one comes back with -EBUSY, and idle threads die after 5 s.
  • A reply backlog also blocks the receive: a transport with no write space isn't queued for reading (svc_xprt_no_write_space).
  • Nothing bounds the unread backlog. TCP svc sockets autotune to tcp_rmem[2], and xeu posts 8 rings × 4096 buffers, one order-0 page each.

So the sub-project may reduce to configuration: make the landing set small and recycled, and make the copy prompt. That is a hypothesis for measurement to settle, not a conclusion.

Mike's question, and David's

This idea doesn't need buffered I/O

"Buffered IO doesn't allow zero copy via O_DIRECT, right?" Right.

A buffered write copies into page-cache folios, and writeback DMAs from those; the RPC buffer never reaches the device. But David's idea already accepts one CPU copy, and its "second copy" is the NVMe DMA out of the copy destination. When the destination is a page-tiled buffer written O_DIRECT, which is today's rq_pages plus nfsd_direct_write, the back end is already zero-copy from the destination. The page cache is one possible destination, not a requirement, and io_cache_write=1 measured 17–38% slower for writes on perflab (2026-09-23).

"Stable writes hold the RPC buffer until the I/O completes; unstable don't" — checked

In copy mode the held buffer is the destination, which is meant to absorb storage latency; the NIC buffer is already gone. What's held that matters is the thread, because only a free thread can do the next copy. The decoupling needed is thread from copy, not buffer from storage.

David's "confine receive buffers to a pool": nothing in this repository confines receive buffers. Loans take plain page references, so pages that nfsd still holds leave the page_pool and the NIC's landing set grows. If David has a separate change, we need it.

Found in review · try first

A zero-copy route on PRP NVMe: paired posting with MSS 8192

The PRP gate tests joints against the 4 KiB segment boundary, not PAGE_SIZE. The existing, untested xeu-hds-experiment patch lands each frame's payload at offset 0 of its own page. Set MTU 8244 on both ends (20 IP + 32 TCP with timestamps + 8192) and every interior payload fragment becomes exactly one 8 KiB block starting at page offset 0:

MTU 8244, hds_hdr_len=66, 64 KiB pages, loans on fragment [off 0, len 8192] end 8192 & 4095 = 0 no joint record's first [off H, to 8192] starts 4-aligned allowed record's last [off 0, len y] allowed → loaned WRITE goes O_DIRECT on PRP NVMe: no SGL, no CPU copy

That costs one out-of-tree driver patch (already written) and an MTU change. It depends on four things: E1 honouring paired posting, TCP headers staying a fixed 66 bytes, the client sending full-MSS segments, and the network carrying MTU 8244. A short segment or odd header demotes only its record, with correct data. The loan is still held until the reply, and each 8 KiB segment occupies a 64 KiB page.

B′ needs three things, all unverified on E1: NIC writes allocate into the system cache; a full-line NIC write to a resident dirty line replaces it with no DRAM write-back; and the copy's destination stores don't evict the landing set. Only C reaches 2 regardless.

tardis1 being DRAM-bandwidth bound is itself unverified. The 72% memory-stall figure fits a latency-bound copy just as well, and no DRAM bandwidth was ever measured. The throughput gain is conditional on phase 0b showing the write run near the DRAM ceiling.

Recommended direction

Probe cheap, gate on hardware, configure before coding

  1. Try Z1 first. If nfsd_write_direct dominates, the write path is zero-copy on PRP NVMe and this sub-project becomes the fallback for networks that can't run MTU 8244.
  2. Decide R1 with an iperf3 small-ring test: no NFS, no NVMe. If NIC writes don't allocate into cache, stop Z4.
  3. Treat today's copy path as the Z4 data path. Write no new data-path code until measurements show it can't reach B′.
  4. Then configuration only: smaller rings (never below 32), tcp_rmem sized in truesize terms, loans off, a fixed nfsd thread count, priority, a dedicated NAPI core, and io_cache_write 2 against 4.
  5. Only if the copy is still thread-bound at io_cache_write=2 with a fixed thread pool: split SUNRPC receive from execution. That is the one substantial kernel change anticipated, and it's upstreamable on its own merits.

Measurement plan · before any code

Each phase ends in a go/no-go

All on tardis1, on the 64 KiB kernel from this tree's HS twin, XFS on the PRP NVMe, with the existing client load (1 client, nconnect 16 × 2 subnets, 1 MB wsize). Cheap tests that can end or redirect the sub-project run first.

Configuration sweep, no kernel change

Rings 4096 → 64, ring count 8 and 4, tcp_rmem in truesize terms, skb_defer_max, nfsd threads with min = max, priority, pinned NAPI, io_cache_write 4 / 2 / 1. Go: a knee near the predicted landing size where touches per byte fall toward 2, with no drops or TCP collapse.

Don't shrink xeu rings below 32: RX stops for good.

The driver refills only when 32 or more slots are free (XEU_RX_REFILL_THRESHOLD, xeu_drv.c:109), and ethtool accepts 16. A ring of 16 can never reach 32 free, so it stalls after the first 16 frames. Phase 1 scales the threshold with the ring size.

Implementation · sketch only

Nothing starts before phase 0 and Mike's go

  • Phase 1, xeu driver: scale the refill threshold with ring size; productize paired posting if Z1 wins. Out-of-tree vendor driver, reported to Xsight.
  • Phase 2, SUNRPC receive/execute split, only if phase 0c shows thread availability bounds the copy. A receive stage fills free arenas and hands complete records to execution threads, with backpressure through the TCP window rather than drops. Exposed as SUNRPC service options.
  • Phase 3, per-service TCP receive-buffer policy, like UDP's svc_sock_setbufsize(), sized in truesize terms, if system-wide tcp_rmem is too blunt.
  • Phase 4, early loan release, in the parent series: only after the whole procedure returns, because decoded NFSv4 arguments such as file names point into loaned NIC pages, and later COMPOUND ops use them. KUnit must cover a WRITE followed by a name-bearing op in one COMPOUND.
  • KUnit in separate commits after each feature. No HS-only shortcuts; module parameters only as kill switches.

Xsight
