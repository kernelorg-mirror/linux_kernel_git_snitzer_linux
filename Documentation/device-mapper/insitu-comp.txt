This is a simple DM target supporting in-place compression for SSD only.
Underlying SSD must support 512B sector size, the target only supports
4K sector size.

Disk layout
===========
|superblock|...metadata...|..data...|

Store unit is 4K (a block).  Superblock is 1 block, which stores
metadata and data sizes and compression algorithm.  Metadata is a
bitmap.  Each data block requires 5 bits of metadata.

Data
----
Data of a block may be compressed.  Compressed data payload is rounded
up to the next 512B sector.  On disk, payload is stored at the beginning
of the block.  For example, say we store data to block A, which starts
at sector B, its original size is 4K, compressed size is 1500.
Compressed data (CD) will use 3 sectors.  The 3 sector payload will be
stored at sector B.

-----------------------------------------------------
... | CD1 | CD2 | CD3 |   |   |   |   |    |    | ...
-----------------------------------------------------
    ^B    ^B+1  ^B+2                  ^B+7

For this block, we will not use sector B+3 to B+7 (a hole).  We use 4
metadata bits to present payload size.  The compressed size (1500) isn't
stored in metadata directly.  Instead, we store it at the last 32bits of
payload.  In this example, we store it at the end of sector B+2.  If
compressed size + sizeof(32bits) crosses a sector, payload size will
increase one sector.  If payload uses 8 sectors, we store uncompressed
data directly.

If IO size is bigger than one block, we can store the data as an extent.
Data of the whole extent will be compressed and stored in the similar
way like above.  The first block of the extent is the head, all others
are the tail.  If extent is 1 block, that block is the head.  We have 1
bit of metadata to present if a block is a head or tail.  If 4 metadata
bits of head block can't store extent payload size, we will borrow the
tail block's meta bits to store payload size.  Maximum allowed extent
size is 128K, so we don't compress/decompress too large a data area.

Metadata
--------
Modifying data will modify metadata too.  Metadata will be written
(flushed) to disk according to the metadata write policy.  Writeback and
writethrough modes are supported.  In writeback mode, metadata will be
written to disk within the specified interval or on a FLUSH request.  In
writethrough mode, data and metadata will be written to disk together.


Constructor
===========

 insitu-comp <ssd dev> [<#feature args> [<feature arg>]*]

 ssd dev	 : underlying SSD device

 Optional feature arguments:

   writethrough: flush metadata to disk using writethrough mode.

   writeback <meta_commit_delay>: flush metadata to disk with writeback
				  mode after <meta_commit_delay> seconds.
